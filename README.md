# Mission Management

Mission Management lets the Launch Portal create a mission in NMDB, configure its platforms and sensors, and generate the mission-specific threat XML and MDF needed for sensor programming.

## Overview

NMDB is the system of record for mission metadata and for the metadata of every artifact generated for a mission. The Launch Portal (LP) owns the mission workflow and approval; once a mission is ready, LP calls NMDB to create and prepare it.

The feature covers four capability areas:

| Area | What it does |
| --- | --- |
| Mission management | Create, retrieve, update, list and soft-delete missions |
| Mission configuration | Assign platform instances and their sensors to a mission |
| Threat library export | Select mission-relevant NRD entities and generate validated threat XML |
| Sensor programming | Generate a mission-specific MDF from threat XML through the ELT workflow |

Generated files live in export storage, not in the database, and are downloadable for a configured period. This page reflects the implemented feature and supersedes the preliminary design where decisions changed during development.

## Scope

| In scope | Out of scope |
| --- | --- |
| Mission creation, retrieval, update, listing and soft deletion | Mission approval and LP workflow state |
| Assigning platform instances and sensors to a mission | SharePoint folder creation and management |
| Selecting threat data and generating validated threat XML | Storing mission documents or generated binaries in the database |
| Generating MDF through the ELT workflow | The vendor ELT tool itself |
| Time-limited download, expiry and cleanup of generated files | Authorization policy definition |
| Keeping artifact history after files are purged | Downstream processing by Thor, Trident or vendor tools |

## Responsibilities

| System | Responsible for |
| --- | --- |
| Launch Portal | Mission workflow and approval, operator interaction, starting Mission Management operations, showing configuration and exports |
| NMDB | Mission metadata, platform and sensor association, NRD data access, threat export and XML validation, MDF integration, artifact metadata and download lifecycle |
| NRD / NALDI | Source threat and technical data for the tree view and threat export |
| ELT tool | Turning threat XML into MDF |
| Kong | Access control in front of the NMDB API |
| Thor, Trident and other consumers | Using mission information and generated artifacts per their own integrations |

## End-to-end flow

A typical mission preparation runs from approval in LP to a downloadable MDF in nine steps.

1. The operator creates and approves the mission in LP.
2. LP creates the mission in NMDB, which returns the Mission ID used by every later call.
3. The operator assigns one or more platform instances.
4. The operator assigns sensors belonging to those platform instances.
5. The operator uses the threat library tree view to filter and select the required NRD entities.
6. LP requests a threat export; NMDB generates the XML from current NRD data and validates it.
7. The threat XML is downloaded and can be checked against NRD/NALDI.
8. When an MDF is needed, the threat XML is submitted for MDF generation; NMDB validates it and runs the ELT process.
9. Threat XML and MDF stay downloadable until expiry, after which the files are purged and their history is kept.

Mission approval stays entirely in LP; NMDB only acts on missions LP has decided to create.

## Missions

A mission is the container for everything else in this feature: it can hold many platform instances, sensors, threat exports and MDFs.

| Field | Description |
| --- | --- |
| Mission ID | Unique identifier generated by NMDB |
| Mission Name | Name of the mission |
| Mission Type | Mission category |
| Classification | Security classification of the mission |
| Status | Mission status held in NMDB |
| Start Date / End Date | Planned mission dates |
| Created By | User or system that created the mission |
| Created At / Updated At | Creation and last-update timestamps |

Missions can be listed with filters on name, start date, end date and last-updated time, with pagination. Updates are partial: only the fields sent are changed.

Deletion is soft. A deleted mission is kept for traceability but no longer appears in retrieval or listing.

## Platform instances and sensors

A mission is configured by assigning platform instances first, then sensors that belong to them. The hierarchy is Platform → Platform Instance → Sensor.

Platform instances come from different operational environments (air, sea surface, subsurface and others). Each is identified within a mission by its platform type plus platform instance ID, so identical IDs from different environments are never treated as the same instance.

NMDB checks the following before accepting an assignment:

- The mission exists.
- Each platform instance exists in its environment's dataset and is not already assigned to the mission.
- The mission has at least one platform instance before sensors are added.
- Each sensor exists in the sensor catalogue and has not already been assigned.
- Each sensor belongs to one of the mission's assigned platform instances.

A sensor from a platform outside the mission is rejected, which stops unrelated equipment entering the mission by mistake.

## Threat library export

A threat export is a mission-specific XML package built from the NRD entities the operator selects, rather than the full NRD dataset.

**Selection.** The tree view lets the operator filter NRD data by categories such as country, domain, platform, platform instance, radar, emitter, emitter group and weapon, then select the entities needed. Filters are only a way to find data: the export is built from the selected entities, limited to the supported NRD entity classes, and the filter criteria are not stored with the mission.

**Generation.** NMDB checks the mission exists, validates the selected entity identifiers, reads the current NRD data, builds the XML, validates it, stores the file and records the export metadata. Because data is read at request time, an export always reflects NRD as it stood when it was generated.

**Content.** Depending on the entities selected, an export can include platforms, platform instances, emitters, radars, weapons, communications entities, sensor technical data, and the relationships between them.

**Validation.** Generated XML is checked against the expected XSD using the same validation used for NRD XML handling. Content that fails is rejected and never offered as a successful export.

**History.** Every generation creates a new export record; earlier exports are never overwritten. Exports for a mission are told apart by generation time.

## Verifying an export against NRD/NALDI

Beyond XSD validation, an export can be checked against its NRD/NALDI source to confirm the selected data is represented correctly. For example: select a radar with object ID X in the tree view, generate the export, find object ID X in the XML, and compare it with the NRD/NALDI record.

| Check | What to confirm |
| --- | --- |
| Object identifier | Exported object ID matches the selected NRD/NALDI object |
| Entity type | Exported entity belongs to the expected NRD class |
| Technical data | Technical attributes match the source |
| Platform association | Sensor and threat associations match the expected platform instance |
| Selection | Every selected entity is present |
| Exclusion | No unrelated, unselected entity appears |
| Structure | XML complies with the expected XSD |

## MDF generation

An MDF is generated from threat XML submitted for the mission: NMDB validates the file, runs the ELT process, stores the MDF and records its metadata for download.

Input rules, checked before ELT runs:

- One XML file per request.
- Maximum size 50 MB.
- The file must be well-formed XML.

If ELT processing fails, the request fails and no MDF is recorded; the operator corrects the input or retries.

The MDF is a mission-level artifact and is not tied to a single sensor. The integration layer is in place, but the final vendor ELT CLI depends on the vendor tool and its invocation contract.

## Generated artifacts

Threat exports and MDFs are temporary files with an expiry time; their metadata is permanent.

| State | Meaning | Download |
| --- | --- | --- |
| Available | File exists and is within its validity period | Yes |
| Expired | Validity period has passed | No |
| Purged | Cleanup has removed the physical file; the metadata record remains as history | No |

Files are kept in the configured export storage location, not in the database. The metadata recorded for each artifact includes mission ID, file type, source filename where relevant, file location, download information, and generated, expiry and purge times.

## API at a glance

All operations sit under the `/missions` resource and are scoped by the NMDB Mission ID. Request and response schemas are in the service's OpenAPI specification.

| Capability | Operations | Resource |
| --- | --- | --- |
| Missions | Create, list, get, update, soft delete | `/missions`, `/missions/{mission_id}` |
| Platform instances | Assign, list | `/missions/{mission_id}/platform-instance` |
| Sensors | Assign, list | `/missions/{mission_id}/sensors` |
| Threat exports | Generate, list history, get details, download | `/missions/{mission_id}/exports/threat` |
| MDF | Generate through ELT | `/missions/{mission_id}/exports/mdf/elt` |

## Business rules

- A mission must exist before any platform, sensor or export operation.
- A platform instance must exist in its environment's dataset and can be assigned to a mission only once.
- A sensor must exist, belong to an assigned platform instance, and can be assigned only once.
- Threat export is limited to supported NRD entity classes and must pass XSD validation to succeed.
- MDF input must be well-formed XML within the 50 MB limit; a failed ELT run records no MDF.
- New threat exports and MDFs never overwrite earlier ones.
- Expired files may be purged; their metadata is always kept.
